## 适用范围与完成标准

本文面向使用 Mihomo 配置的桌面客户端，不把不同软件的按钮名称混为一谈。准备客户端完整名称、版本、服务方提供的 Clash / Mihomo 配置地址，以及原来可用的配置备份。订阅地址常含账户令牌，记录问题时只保留域名和错误类型。

完成导入需要四个证据：下载成功、内容可解析、当前配置确实启用、一次实际请求命中预期策略。节点列表出现只能证明其中一部分。

## 第一步：确认拿到的是配置地址

在服务方账户页选择 Clash 或 Mihomo 对应的订阅入口，不复制登录页、付款页或浏览器地址栏里的后台页面。复制后检查开头的协议、结尾是否完整，避免把中文标点或换行一起带入。

在客户端的订阅 / 配置页面添加新条目，使用“服务名＋日期”作为本地名称，先保留旧条目。执行一次更新，记下时间和错误原文，不要连续点击刷新来掩盖第一次失败。

| 观察结果 | 可以下的结论 | 下一步 |
| --- | --- | --- |
| HTTP 401 / 403 | 服务器拒绝了本次请求 | 核对令牌、账户状态、服务方访问要求；不能仅凭状态码断言到期 |
| HTTP 404 | 此路径当前不存在或被隐藏 | 从服务方重新复制，不自行猜路径 |
| HTTP 200 但返回 HTML | 网络请求成功，内容不是预期配置 | 检查是否登录页、验证页或跳转提示 |
| YAML 行号错误 | 已进入解析阶段 | 保存原文件；核对格式，不先换 DNS |
| 更新完成但节点为空 | 仍不能证明配置可用 | 检查提供商文件、筛选条件和订阅格式 |

## 第二步：验证配置，而不是只改扩展名

把网页另存为 .yaml 不会让网页变成配置。完整配置可能直接包含 proxies，也可能引用 proxy-providers；不能只因没有内联节点便判断文件损坏。检查客户端日志里是否还有提供商下载错误。

熟悉命令行的读者可以用与客户端相同版本的核心，对文件副本执行配置检查。单独核心检测成功只代表该核心接受配置，不能保证客户端覆写后仍相同，也不能保证远端节点可连接。[本地实验记录](/articles/mihomo-local-lab/)给出了有效配置与故意破坏 YAML 的对照结果。

## 第三步：激活后做一次请求

选中新配置，确认界面显示它处于使用状态，再选择策略组中的一个明确节点。先使用规则模式和一种接管方式，打开一个你有权访问的测试页面；同时查看连接记录中的目标、命中规则和出口。若连接记录完全没有出现，先排查应用是否进入代理，不要立即归咎于订阅。

如果策略组选择了自动策略，保存测试时实际选中的节点名称，否则下一次结果难以比较。延迟数字只是测试请求的结果，不等于整个订阅已经验证可用。

## 第四步：更新失败时保留可用状态

更新前记录当前配置名、节点数和所用策略。失败后确认旧配置是否仍在运行；只回到已知可用配置，不把新下载文件覆盖到唯一备份。反馈时提供客户端版本、发生时间、状态码或脱敏日志、复现步骤，不公开完整订阅链接。
